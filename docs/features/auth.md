# 인증과 로그인

## 사용자 목표

사용자는 본인 계정으로 안전하게 로그인하고, 관리자에게 승인된 가정에만 접근한다.

## 핵심 원칙

- 사용자가 사용하는 계정 ID와 로그인 ID는 이메일 주소다.
- 내부 데이터 관계에는 변경 불가능한 UUID 형식의 `user_id`를 사용한다.
- 사용자 인증과 가족 구성원 승인을 분리한다.
- 로그인 성공만으로 가정 데이터 접근 권한을 부여하지 않는다.
- 가정 데이터 접근에는 `active` 구성원 관계가 필요하다.
- 관리자가 다른 사용자의 비밀번호를 생성하거나 전달하지 않는다.

## MVP 포함 범위

- 이메일 주소를 계정 ID로 사용하는 최초 관리자 가입과 로그인
- 가입할 사용자의 개인 이메일 주소로 1회용 가입 경로 발송
- 초대받은 사용자의 본인 계정 활성화
- 로그아웃과 세션 만료 처리
- 탈퇴 또는 정지된 구성원의 세션 접근 차단

## 후속 확장 범위

- Google OAuth 로그인
- Google 계정의 가족 가입 요청
- 관리자의 가입 승인 또는 거절
- 기존 이메일 계정과 Google 계정 연결

## 로그인 후 접근 판정

1. 인증 제공자가 사용자 신원을 확인한다.
2. 시스템이 사용자의 가정 구성원 관계를 조회한다.
3. `active` 관계가 있으면 해당 가정으로 이동한다.
4. 초대가 있으면 초대 수락 화면으로 이동한다.
5. 가입 요청이 `pending`이면 승인 대기 화면을 표시한다.
6. 어느 조건에도 해당하지 않으면 가정 접근을 허용하지 않는다.

## Google 계정 연동 원칙

- Google에서 제공한 고유 사용자 ID를 외부 계정 식별자로 저장한다.
- Google이 확인한 이메일이 기존 계정 ID와 일치하더라도 최초 연결 시에는 명시적 계정 연결 확인을 거친다.
- Google 이메일 주소와 내부 `user_id`를 동일한 값으로 사용하지 않는다.
- 계정 연결에는 현재 계정 재인증 또는 명시적 확인 절차가 필요하다.
- Google OAuth token과 client secret은 브라우저에 노출하지 않는다.
- 필요한 최소 OAuth scope만 요청한다.

Google Calendar 권한은 Google 로그인 권한과 별도로 요청할 수 있게 설계한다. Google로 로그인했다고 해서 Calendar 접근 권한을 자동 요청하지 않는다.

## 계정 식별 규칙

사용자 관점에서는 이메일 주소가 계정 ID다.

```text
로그인 ID: climax1123@gmail.com
내부 user_id: 7dd53ab2-...-4f86
Google 연결 ID: Google provider의 고유 sub 값
```

이메일 주소를 DB 기본키로 직접 사용하지 않는 이유는 이메일 주소 변경, Google 계정 연결, 작성 이력 보존과 개인정보 노출 최소화를 지원하기 위해서다. 이메일을 변경하더라도 내부 `user_id`와 기존 거래·일정·감사 이력은 유지한다.

## 인수 조건

- 인증되지 않은 사용자는 보호된 화면에 접근할 수 없다.
- 인증됐지만 승인되지 않은 사용자는 가정 데이터에 접근할 수 없다.
- `active` 구성원만 공유 기능을 이용할 수 있다.
- 관리자가 탈퇴 또는 정지 처리한 사용자는 기존 세션에서도 차단된다.
- 인증 실패, 초대 대기와 승인 대기 상태를 구분해 안내한다.

## 필수 테스트

- 비로그인 사용자의 보호 화면 접근 차단
- 활성 구성원의 정상 접근
- 승인 대기 사용자의 데이터 접근 차단
- 정지·탈퇴 사용자의 기존 세션 접근 차단
- 초대 수락 후 접근 권한 생성
- 향후 Google 계정 연결 시 중복 계정 방지
