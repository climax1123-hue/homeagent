# statement-classification - Plan Document

> Version: 0.1.0 | Date: 2026-08-28 | Status: Approved
> Level: Dynamic

## 1. 목적

은행·카드 명세를 가져올 때 거래처와 메모를 기준으로 카테고리를 자동 추천해 반복 분류 작업을 줄인다. 추천 결과는 바로 저장하지 않고 사용자가 미리보기에서 확인·수정한다.

## 2. 목표

- 거래처·메모 키워드에 맞는 카테고리를 추천한다.
- 사용자가 추천 이유를 쉽게 확인한다.
- 규칙의 우선순위와 활성 상태를 관리한다.
- 가족 장부와 개인 장부의 규칙 및 권한을 분리한다.
- 명세 가져오기 화면에서 추천 카테고리를 거래별로 수정한다.
- 은행별로 다른 열 구성을 양식 프로필로 저장하고 다음 업로드에서 재사용한다.

## 3. 포함 범위

- `포함` 및 `정확히 일치` 방식의 규칙 기반 분류
- 거래처, 메모 또는 두 필드 모두를 대상으로 검색
- 수입·지출별 카테고리 연결
- 우선순위가 가장 높은 규칙 한 개를 추천
- 명세 미리보기의 추천 카테고리와 적용 규칙 표시
- 규칙 추가·수정·비활성화·우선순위 관리
- 가족 장부 규칙은 관리자, 개인 장부 규칙은 소유자만 관리
- `household_id`, `book_id` 격리와 RLS
- 정규화된 헤더 signature로 저장된 은행 양식 자동 탐색
- 인코딩·시트·열 매핑을 장부별 양식 프로필로 저장·수동 재선택
- 저장 양식이 없거나 적용에 실패하면 자동 탐지와 수동 매핑으로 fallback

## 4. 제외 범위

- AI/ML 모델을 이용한 분류
- 사용자의 수정 결과를 자동 학습
- 정규식과 임의 스크립트 실행
- 은행 Open API 연결
- 기존 원장 전체를 자동 재분류

## 5. 사용자 흐름

```text
가계부 → 명세 가져오기 → 파일 분석
→ 거래처·메모와 분류 규칙 비교
→ 추천 카테고리와 추천 이유 표시
→ 사용자가 행별 확인·수정
→ 선택 거래 반영

가계부 → 분류 규칙 관리
→ 키워드·대상 필드·카테고리·우선순위 설정
```

## 6. 기능 요구사항

| ID    | 요구사항                                                       |
| ----- | -------------------------------------------------------------- |
| FR-01 | 접근 가능한 장부의 활성 분류 규칙만 조회한다.                  |
| FR-02 | 거래 유형과 카테고리 유형이 일치해야 한다.                     |
| FR-03 | 거래처·메모를 공백 정리 및 소문자 변환 후 비교한다.            |
| FR-04 | 여러 규칙이 맞으면 우선순위가 높은 규칙을 사용한다.            |
| FR-05 | 추천 카테고리와 일치한 키워드를 미리보기에 표시한다.           |
| FR-06 | 사용자가 추천을 변경하거나 미분류로 되돌릴 수 있다.            |
| FR-07 | 가족 장부 규칙은 관리자만 관리한다.                            |
| FR-08 | 개인 장부 규칙은 해당 장부 소유자만 관리한다.                  |
| FR-09 | 비활성화한 규칙은 추천에 사용하지 않는다.                      |
| FR-10 | 추천 실패가 명세 가져오기 자체를 막지 않는다.                  |
| FR-11 | 사용자가 확정한 은행 열 매핑을 장부별 양식으로 저장한다.       |
| FR-12 | 같은 헤더의 파일에는 저장된 양식을 자동으로 적용한다.          |
| FR-13 | 자동 적용이 실패하면 저장 양식 선택 또는 수동 매핑이 가능하다. |
| FR-14 | 가족 양식은 관리자, 개인 장부 양식은 소유자만 관리한다.        |

## 7. 데이터 모델 후보

### `ledger_classification_rules`

- `id`, `household_id`, `book_id`
- `transaction_type`: income/expense
- `target_field`: merchant/memo/both
- `match_type`: contains/exact
- `keyword`, `normalized_keyword`
- `category_id`, `priority`, `is_active`
- `created_by`, `created_at`, `updated_at`

원본 금융정보와 거래 내역은 규칙 테이블에 저장하지 않는다.

### `ledger_statement_profiles`

- `id`, `household_id`, `book_id`, 표시 이름
- 정규화 헤더 SHA-256 signature
- 열 mapping JSON, CSV encoding, XLSX sheet 이름
- 활성 상태, 생성 사용자와 생성·수정 시각
- 원본 파일과 실제 금융 거래 행은 저장하지 않음

## 8. 비기능 요구사항

- 최대 10,000행 추천이 브라우저 UI를 장시간 멈추게 하지 않는다.
- 키워드는 2~100자로 제한하고 제어문자를 제거한다.
- 추천 결과는 설명 가능해야 하며 자동 확정하지 않는다.
- 모든 공개 테이블에 RLS를 적용한다.
- 카테고리·장부·가족 공간의 교차 참조를 DB에서 거부한다.
- PC와 390px 모바일에서 규칙 및 추천 결과를 확인할 수 있다.

## 9. 성공 기준

- [ ] `스타벅스 강남점`이 `스타벅스` 포함 규칙으로 카페 카테고리를 추천한다.
- [ ] 수입 규칙이 지출 거래에 적용되지 않는다.
- [ ] 우선순위가 높은 규칙이 안정적으로 선택된다.
- [ ] 추천 카테고리를 사용자가 행별로 변경할 수 있다.
- [ ] 구성원은 가족 장부 규칙을 변경할 수 없다.
- [ ] 다른 가족과 개인 장부의 규칙을 조회할 수 없다.
- [ ] 규칙이 없어도 명세를 정상 반영할 수 있다.
- [ ] 저장한 은행 양식이 같은 헤더의 다음 파일에 자동 적용된다.
- [ ] 처음 보는 은행 양식은 수동 매핑 후 저장할 수 있다.
- [ ] lint, TypeScript, 단위 테스트, RLS 테스트와 build가 통과한다.

## 10. 위험과 대응

| 위험                      | 대응                                                |
| ------------------------- | --------------------------------------------------- |
| 너무 넓은 키워드로 오분류 | 최소 길이, 추천 이유 표시, 사용자 최종 확인         |
| 여러 규칙 충돌            | 명시적 우선순위와 안정적인 보조 정렬                |
| 권한 없는 규칙 변경       | RLS와 DB trigger/RPC 이중 검증                      |
| 대량 행 성능 저하         | 정규화된 규칙을 한 번 조회해 브라우저에서 일괄 비교 |
