> Version: 1.0.0 | Date: 2026-08-26 | Status: Completed

## 1. Overview

### 1.1 Purpose

가족이 일정, 가계부, 디데이와 목표 데이터를 안전하게 공유할 수 있도록 `household`를 최상위 보안·데이터 경계로 만들고, 관리자가 가족 구성원의 초대와 접근 상태를 관리할 수 있게 한다.

### 1.2 Background

초기 사용자는 관리자 1명과 이메일로 초대받은 배우자 1명이다. 향후 사용자와 가정 수가 늘어나더라도 서로의 데이터를 볼 수 없도록 모든 업무 데이터는 `household_id`로 격리되어야 한다.

인증 기능은 사용자의 신원과 로그인 세션을 확인하고, household 기능은 해당 사용자가 어느 가정에 어떤 역할과 상태로 소속되는지를 결정한다. 로그인 성공만으로 가정 데이터 접근 권한을 부여하지 않는다.

## 2. Goals

### 2.1 Primary Goals

- [ ] 최초 인증 사용자가 가정을 만들고 원자적으로 `active admin` 구성원이 된다.
- [ ] 관리자가 특정 이메일 주소로 만료 시간이 있는 1회용 가족 초대를 생성하고 취소할 수 있다.
- [ ] 초대받은 사용자가 이메일 소유 확인 후 초대를 한 번만 수락하여 `active member`가 된다.
- [ ] 관리자가 같은 가정의 구성원 목록을 조회하고 구성원을 정지, 재활성화 또는 탈퇴 처리할 수 있다.
- [ ] 비관리자와 다른 가정 사용자의 관리 작업 및 데이터 접근을 DB RLS와 서버 검증으로 차단한다.
- [ ] 주요 구성원·초대 상태 변경을 감사 가능한 형태로 기록한다.

### 2.2 Non-Goals

- Google 로그인 사용자의 가정 검색 및 가입 요청·승인 흐름
- 관리자 승격·위임과 복수 관리자 운영 정책
- 구성원의 자발적 탈퇴 요청 및 관리자 계정 분실 복구 절차
- 일정, 가계부, 디데이, 목표 등 개별 업무 기능 구현
- 이메일 발송 사업자와 운영 요금제의 최종 선정

## 3. Scope

### 3.1 In Scope

#### 가정 생성

- 인증된 최초 사용자의 가정 생성
- 가정과 최초 `admin` 구성원 관계의 원자적 생성
- 한 사용자의 동일 가정 내 중복 구성원 관계 방지

#### 이메일 초대

- 관리자만 초대 생성·목록 조회·취소 가능
- 이메일 앞뒤 공백 제거 및 대소문자를 구분하지 않는 비교
- 활성 구성원 및 유효한 중복 초대 차단
- 만료 시간이 있는 1회용 초대와 원문 대신 토큰 해시 저장
- 로그인 계정 이메일과 초대 이메일 일치 확인
- 초대 수락과 구성원 생성을 하나의 트랜잭션으로 처리
- 수락, 만료, 취소 또는 재사용된 초대 차단

#### 구성원 관리

- `admin`, `member` 역할과 `active`, `suspended`, `removed` 상태
- 관리자의 같은 가정 구성원 목록 조회
- 관리자의 구성원 정지, 재활성화 및 soft removal
- 정지·탈퇴 직후 기존 세션을 포함한 가정 데이터 접근 차단
- 마지막 활성 관리자 제거 또는 권한 해제 차단
- 과거 공유 데이터와 작성자 이력 보존

#### 보안과 감사

- 모든 관련 레코드의 `household_id` 기반 격리
- 공개 업무 테이블에 RLS 적용
- 관리자 mutation에 서버와 DB 양쪽 권한 검증
- 초대 및 구성원 상태 변경의 행위자, 대상, 가정, 시각 기록
- 초대 토큰과 인증 자격 증명을 로그에 기록하지 않음

### 3.2 Out of Scope

- Google OAuth 자체 구현과 Google 사용자의 `join_request`
- 가족 코드, 관리자 이메일 등 가정 검색 방식
- 관리 역할 변경 UI와 다중 관리자 정책
- 탈퇴 사용자의 자동 재가입 및 기존 구성원 관계 복구
- 이메일 템플릿의 시각 디자인과 대규모 메일 발송 최적화

## 4. Functional Requirements

| ID        | Requirement                                                                           |
| --------- | ------------------------------------------------------------------------------------- |
| HH-FR-001 | 인증 사용자는 가정을 생성하고 최초 활성 관리자가 될 수 있다.                          |
| HH-FR-002 | 활성 관리자만 같은 가정의 구성원과 초대 목록을 조회할 수 있다.                        |
| HH-FR-003 | 활성 관리자는 아직 구성원이 아니며 유효한 초대가 없는 이메일로 초대를 생성할 수 있다. |
| HH-FR-004 | 활성 관리자는 처리되지 않은 초대를 취소할 수 있다.                                    |
| HH-FR-005 | 이메일이 일치하는 인증 사용자만 유효한 초대를 한 번 수락할 수 있다.                   |
| HH-FR-006 | 초대 수락 시 사용자는 해당 가정의 활성 일반 구성원이 된다.                            |
| HH-FR-007 | 활성 관리자는 일반 구성원을 정지, 재활성화 또는 탈퇴 처리할 수 있다.                  |
| HH-FR-008 | 정지·탈퇴 구성원과 미승인 사용자는 가정 업무 데이터에 접근할 수 없다.                 |
| HH-FR-009 | 다른 가정의 사용자와 일반 구성원은 관리자 작업을 수행할 수 없다.                      |
| HH-FR-010 | 주요 초대·구성원 상태 변경은 감사 로그에 남는다.                                      |

## 5. Non-Functional Requirements

- **Security:** 클라이언트가 전달한 `household_id`, role 또는 status를 신뢰하지 않고 현재 DB 상태를 기준으로 매 요청을 검증한다.
- **Privacy:** 이메일과 사용자 식별 정보의 노출을 최소화하며 실제 개인정보를 테스트 fixture에 사용하지 않는다.
- **Consistency:** 초대 수락, 가정 생성과 최초 관리자 생성은 부분 성공이 없도록 트랜잭션으로 처리한다.
- **Time:** 시각은 UTC로 저장하고 화면에서는 기본적으로 `Asia/Seoul`로 표시한다.
- **Usability:** PC와 모바일 반응형 화면을 제공하고 주요 터치 영역은 최소 44px로 만든다.
- **Maintainability:** 인증 공급자와 이메일 발송 수단이 바뀌어도 구성원·초대 도메인 규칙은 유지되도록 분리한다.
- **Extensibility:** 향후 `join_requests`와 복수 관리자 정책을 추가할 수 있도록 인증, 초대, 구성원 관계를 분리한다.

## 6. Success Criteria

- [ ] 최초 사용자의 가정과 관리자 관계가 함께 생성되며 한쪽만 남는 부분 실패가 없다.
- [ ] 관리자가 배우자 이메일로 초대하고, 해당 사용자가 이메일 확인 후 정확히 한 번 수락할 수 있다.
- [ ] 중복·만료·취소·재사용 초대와 이메일 불일치 수락이 모두 차단된다.
- [ ] 일반 구성원의 관리자 작업과 다른 가정의 조회·변경이 RLS 테스트에서 차단된다.
- [ ] 구성원을 정지 또는 탈퇴 처리하면 기존 세션에서도 가정 데이터 접근이 즉시 차단된다.
- [ ] 마지막 활성 관리자를 제거할 수 없다.
- [ ] 초대와 구성원 상태 변경이 민감 정보 없이 감사 로그에 기록된다.
- [ ] PC 및 모바일 너비에서 구성원·초대 핵심 흐름을 사용할 수 있다.
- [ ] 관련 테스트, TypeScript, lint와 프로덕션 빌드가 통과한다.

## 7. Architecture Considerations

예상 핵심 엔티티는 `households`, `household_members`, `household_invitations`, `audit_logs`이다. 향후 `household_join_requests`를 별도 엔티티로 추가한다. 구체적인 컬럼, 제약조건, 인덱스, RLS 정책, RPC/API와 화면 흐름은 Design 단계에서 확정한다.

`service_role`과 초대 원문 토큰은 브라우저에 노출하지 않는다. 초대 수락과 관리자 상태 변경처럼 권한과 원자성이 중요한 작업은 보안 정의 함수 또는 신뢰할 수 있는 서버 경계를 사용한다.

## 9. Risks & Mitigations

| Risk                               | Impact   | Probability | Mitigation                                                                      |
| ---------------------------------- | -------- | ----------- | ------------------------------------------------------------------------------- |
| 잘못된 RLS로 다른 가정 데이터 노출 | Critical | Medium      | 모든 공개 업무 테이블에 RLS를 적용하고 교차 가정 권한 테스트를 필수화한다.      |
| 초대 링크 탈취·재사용              | High     | Medium      | 짧은 만료, 1회 사용, 토큰 해시 저장, 이메일 일치 검증을 적용한다.               |
| 관리자 제거로 가정 관리 불가       | High     | Low         | 마지막 활성 관리자 변경을 기본 차단하고 향후 복구 정책을 별도로 설계한다.       |
| 초대 수락 중 부분 실패             | High     | Medium      | 초대 상태와 구성원 생성을 단일 트랜잭션으로 처리한다.                           |
| Auth와 household 책임 중복         | Medium   | Medium      | 인증은 신원, household는 소속·역할·상태를 담당하도록 API와 문서를 분리한다.     |
| 이메일 무료 요금제·전송 제한       | Medium   | Medium      | 공급자를 추상화하고 초기에는 소수 가족 사용량에 맞춰 제한과 재시도 정책을 둔다. |

## 10. Open Decisions for Design

- 초기 버전에서 관리자를 1명으로 고정할지, 복수 관리자를 허용할지
- 초대 기본 유효기간과 만료 후 재발송·재초대 방식
- 회원가입 직후 가정 생성 선택과 초대 수락 분기 방식
- `removed` 사용자의 재초대 시 기존 관계를 복구할지 새 이력을 만들지
- 감사 로그의 보존 기간과 관리자 조회 범위
- Supabase 기본 이메일 발송을 사용할 기간과 외부 메일 공급자 전환 기준

정책이 확정되기 전까지 역할 변경은 제공하지 않고 마지막 활성 관리자 제거를 차단한다.
